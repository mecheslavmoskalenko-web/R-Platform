# План синхронизации Р-Платформа ↔ NetBox

Проект: ПАК ИСБ, объект СКК «Мрия». Документ описывает переход роли источника истины по локациям от Р-Платформы к NetBox.

Последнее обновление: 20.08.2026

---

## Замысел

Роль источника истины по дереву локаций переходит от Р-Платформы к NetBox в два этапа, привязанных к готовности API у подрядчика.

```
        ЭТАП 1 — сейчас                    ЭТАП 2 — после сдачи работ

   ┌──────────────────┐                  ┌──────────────────┐
   │   Р-Платформа    │ источник истины  │      NetBox      │ источник истины
   └────────┬─────────┘                  └────────┬─────────┘
            │ выгрузка из БД                      │ Ansible → REST API
            │ загрузка вручную                    │ автоматически
            ▼                                     ▼
   ┌──────────────────┐                  ┌──────────────────┐
   │      NetBox      │                  │   Р-Платформа    │
   └──────────────────┘                  └──────────────────┘
```

---

## Этап 1. Р-Платформа — источник истины

**Пока подрядчик формирует БД.**

Дерево локаций ведётся в Р-Платформе. В NetBox данные попадают выгрузкой из БД и загрузкой вручную — односторонне, по мере готовности разделов.

### Порядок работ

1. Подрядчик формирует и правит структуру локаций в Р-Платформе
2. Снимается резервная копия БД `core`
3. Из бэкапа выгружается таблица `locations`:

   ```
   pg_restore -t locations -t locationtyps --no-owner --no-privileges \
     -f locations.txt core_<дата>.backup
   ```

4. Дерево преобразуется в файлы импорта и загружается в NetBox
5. Результат сверяется, цикл повторяется по мере правок подрядчика

### Условия этапа

- Запись локаций в NetBox закрыта правами — иначе ручные правки будут молча затираться при следующей загрузке
- Направление одностороннее: Р-Платформа → NetBox

---

## Этап 2. NetBox — источник истины

**После сдачи работ подрядчиком и получения API.**

Новые и изменённые локации заводятся в NetBox и синхронизируются в Р-Платформу через REST API средствами Ansible.

### Порядок работ

1. Оператор создаёт локацию в NetBox
2. Ansible вызывает API Р-Платформы (`s_set_locations`)
3. Платформа присваивает `locid` из последовательности `sq_locations` и возвращает его
4. Ansible записывает `locid` обратно в NetBox в поле `rplatform_locid`
5. По расписанию выполняется сверка полного дерева — реконсиляция и починка расхождений

### Механика

Оперативность обеспечивают штатные Event Rules и вебхуки NetBox: на создание объекта сразу дёргается приёмник. Ansible при этом работает как сверка по расписанию — проходит дерево целиком и устраняет расхождения после сбоев. Одно другому не мешает.

---

## Ограничения проекта

**Р-Платформа остаётся в стоковой версии.** Кастомная сборка не подлежит обновлению производителем, поэтому изменения схемы БД, добавление полей и правка кода исключены. Допустимы только настройка штатных механизмов и работа с данными.

**Целевая структура локаций утверждается заказчиком** и согласуется с техподдержкой производителя. Изменения в неё вносятся только по решению заказчика.

## Что требуется от подрядчика

### Настройка штатных механизмов — под этап 2

1. **Внешний идентификатор NetBox через объектные свойства.** Доработка не требуется: в платформе есть штатный механизм пользовательских свойств, покрывающий задачу полностью.

   | Элемент | Назначение |
   |---|---|
   | `objectproptyps` | типы свойств |
   | `objectprops` | определения свойств, есть флаг **`uniquefl`** |
   | `objectproptpl` | шаблоны наборов свойств |
   | `locations.objectproptplid` | привязка шаблона к локации |
   | `locations.jsonprops` | значения свойств конкретной локации |

   Порядок настройки: завести свойство «Идентификатор NetBox» с признаком уникальности, включить его в шаблон свойств локаций, привязать шаблон к дереву. Значение хранится в `jsonprops`.

   Готовые функции под это:

   - `s_set_objectprops(jsonb)` — определение свойства
   - `s_find_by_jsonprops(v_tablenam text, v_json_props jsonb) RETURNS SETOF integer` — **поиск локации по значению свойства**, то есть готовый механизм идемпотентного сопоставления
   - `s_check_unique_objectprops(jsonb)` — контроль уникальности
   - `s_merge_jsonprops`, `s_get_jsonprops` — работа со значениями

   Механизм доступен и на `equipments`, `departments`, `orgs`, `sysusers`, `systems`, `syspositions` — тот же подход применим при расширении синхронизации на оборудование.

2. **Публикация API на запись** — `s_set_locations`, с возвратом присвоенного `locid` в ответе. Функция в БД уже реализована: `s_set_locations(v_json_params jsonb) RETURNS text`.

   Требуется от подрядчика: подтвердить, что HTTP-доступ к функциям входит в штатную поставку, и предоставить описание формата параметров и кодов возврата. Если API стоковый — это вопрос конфигурации и документации, а не разработки.

### Правка данных — можно начинать сейчас

Не требует изменений в коде, выполняется в интерфейсе платформы:

- **18 дублей наименований** — два здания «КНС», две «Служебные территории», два «Объекты критической инфраструктуры», пять пар помещений «1», два «Вестибюль (1)». В NetBox имена `Site` уникальны глобально, `Location` — в пределах пары «сайт + родитель»
- **21 наименование с артефактами экранирования** — `Вилла кафе \"Тепяньяки\"`, `-1 этаж\прачечная`
- **32 помещения без этажа** — подчинены зданию напрямую
- **2 объекта вне структуры** — узел «Неизвестные» висит на корне
- **5 зданий без координат**

Перечень с полными путями и `locid` — в файле `problems_to_fix.csv` (хранится локально).

Полный свод требований к наименованиям — в [TSO / namingrules/current/TSO/location_naming_rules.md](https://github.com/mecheslavmoskalenko-web/TSO/blob/main/namingrules/current/TSO/location_naming_rules.md).

### Справочник типов локаций

Переименование `varnam` в `locationtyps` — операция над данными. Единственное ограничение: `locBuilding` зашит в пяти местах SQL-кода (две функции и представление `v_reputils_buildings`), его не трогаем. По остальным типам требуется проверка, не ссылается ли на них фронтенд и драйверы интеграции.

## Разграничение зон ответственности

| Область | Источник истины |
|---|---|
| Дерево локаций | этап 1 — Р-Платформа, этап 2 — NetBox |
| Оборудование безопасности, события, состояния | Р-Платформа |
| Сеть, IP-адресация, VLAN, префиксы | NetBox |
| Стойки, порты, кабели, монтажные позиции | NetBox |

Синхронизируется только пересечение — дерево локаций. Остальное живёт в своей системе и не переносится. В частности, номера юнитов и раскладка по стойкам ведутся исключительно в NetBox и доработки Р-Платформы не требуют.

## Принятая модель соответствия

| Уровень Р-Платформы | Модель NetBox |
|---|---|
| `locRegion` — страна, республика, округ, город, село | `dcim.Region` (рекурсивная) |
| `locProvince` — объект / площадка | **`dcim.Site`** — граница между географией и внутренностями |
| `locBuilding` — здание, блок | `dcim.Location` (рекурсивная) |
| `locFasad`, `locFloor`, `locRoom` | `dcim.Location` |
| Функциональное назначение | `extras.Tag` |

**Граница `Site` = площадка**, а не здание. Основание: подсети нарезаны по подсистемам (СКУД, СОТ, ОПС) и сквозные по всему комплексу. У префикса в NetBox одна область видимости, поэтому привязать сквозной префикс к 153 отдельным зданиям невозможно. Подсистемы разделяются ролью префикса — `ipam.Role`.

**`dcim.SiteGroup` не используется** (решение от 19.08.2026): площадок немного, группировка избыточна.

Функциональное назначение вынесено из иерархии в теги: признак сквозной, деревом не выражается. Объект поселения может содержать подобъекты критической инфраструктуры — дизель-генераторная в Винном парке относится к обеим категориям одновременно. В Р-Платформе для этого есть штатный механизм: таблица `public.tags` и поле `tagids` на 12 таблицах, включая `equipments`.

---

## Ключ связи

Кастомное поле **`rplatform_locid`** (integer) на `Region`, `Site`, `Location` в NetBox.

На этапе 2 добавляется обратная связь — идентификатор NetBox в `jsonprops` Р-Платформы через штатный механизм объектных свойств.

## Открытые вопросы

Решения по пунктам 1 и 2 затрагивают целевую структуру и принимаются заказчиком по согласованию с техподдержкой производителя.

1. **`locStreet`** — оставить в резерве под адресный уровень или задействовать под протяжённые элементы объекта: периметр, набережную, акваторию, парковку
2. **Стойки в Р-Платформе** — нужны ли операторам ИСБ как место размещения оборудования. Если нужны, требуется отдельный тип локации, поскольку стойка и прочее движимое имущество соответствуют разным моделям NetBox (`dcim.Rack` и `dcim.Device`). Если не нужны — стойки заводятся только в NetBox и вопрос снимается
3. **Синхронизация оборудования** — переносить ли `equipments` в `dcim.Device` или ограничиться деревом локаций
4. **Штатность HTTP API** — входит ли доступ к функциям `s_get_*` / `s_set_*` в стоковую поставку. Уточняется у подрядчика и техподдержки
5. **Формат ответа `s_set_locations`** — объявлена как `RETURNS text`, фактическое содержимое ответа требует уточнения
